### Automatic coordinator — isolated engineering closed, production rollout gated

- `SupervisorSignedCoordinationService` is now wired to the Nest module with guarded `/engineering/supervisor/system/signed-review/advance`. Internal auto-scan requires ALL THREE production-config opt-ins: `ATLAS_SUPERVISOR_SIGNED_ATTESTATION_MODE=required`, `ATLAS_SUPERVISOR_SIGNED_COORDINATION_MODE=enabled`, and `ATLAS_SUPERVISOR_SIGNED_COORDINATION_SINGLETON_CONFIRMED=true`; optional scan interval `ATLAS_SUPERVISOR_SIGNED_COORDINATION_INTERVAL_MS` range 5000–300000 (default 30000). By default all existing production deployments remain OFF; do not enable until independent release authorization and evidence exist.
- Each scan advances one durable task step: a completed implementation passes a fresh DB-ledger Ed25519 claim/completion check AND publication verifier before existing `AgentGatewayService.submitImplementationFromExecution`; then existing `AgentSupervisorService.beginVerification`; then ONE verifier dispatch; after independently signed verifier completion it calls `PrismaSupervisorSignedReviewStore.releaseReady` with the actual DB task version, verifying both proof pairs and GitHub HEAD and releasing locks in one transaction. No auto merge/deploy or worker READY permission. Failure/cancelled verifier blocks auto retry; history and >50 active tasks cannot permanently starve scans. Production scanning uses an indexed, DB-filtered 50-ID projection (`status IN (WORKING, IMPLEMENTED, VERIFYING)`, ORDER BY createdAt/id, LIMIT/OFFSET); it does NOT periodically load full historic task objects into API memory. Isolated test fallback uses in-memory listTasks only when PrismaService is not injected.
- Actual disposable PostgreSQL test uses REAL AgentSupervisorService+AgentGatewayService+WorkerDispatcherService+signed stores+auto-scan, with TWO local signer keypairs, WORKING/evidence=null -> IMPLEMENTED -> VERIFYING -> verifier QUEUED -> READY, including lock release.
